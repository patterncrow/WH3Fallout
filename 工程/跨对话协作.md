# 已有五个聊天的主从协作

A整体工程与关键任务对话按已有授权统筹四个领域聊天。通信不自动恢复游戏测试，也不构成提交、推送或部署授权。

## 固定角色

| 职责 | 已有聊天ID |
|---|---|
| 唯一主控A | `01a18c35-fe7f-7e70-bbdf-287ab863baed` |
| 种族与派系设计 | `01a19bfd-f717-7061-ad97-fe16fa4f13e3` |

保留原线程与历史。领域聊天仅执行A分配的本领域工作，在原聊天最终回复交接；A读取回传，领域不需要主动给A发消息。由A维护共享工程状态及日志，其他领域维护自己的责任正文。

## 桥接入口

`scripts/codex_chat_bridge.py`使用当前桌面应用提供的原生本地工具管道，提供`read_thread`、`send_message_to_thread`、`wait_threads`。没有创建第二个app-server，也不写聊天数据库、不读取认证文件、不开放网络端口、不修改全局MCP配置。

必须在Codex命令执行环境中调用，继承`CODEX_APP_TOOLS_PIPE_PATH`、`CODEX_THREAD_ID`和`CODEX_TOOL_CALL_ID`。脚本只读查询调用者历史以取得真实轮次；禁止手动覆盖调用者身份。仅A和本次安装聊天可派发，只允许这五个目标；领域不能横向派发。

从项目目录调用，参数文件使用UTF-8 JSON：

```powershell
& C:/Python314/python.exe scripts/codex_chat_bridge.py read_thread --args-file work/codex-coordination/read.json --output work/codex-coordination/read-result.json
& C:/Python314/python.exe scripts/codex_chat_bridge.py send_message_to_thread --args-file work/codex-coordination/task.json --output work/codex-coordination/task-sent.json
& C:/Python314/python.exe scripts/codex_chat_bridge.py wait_threads --args-file work/codex-coordination/wait.json --output work/codex-coordination/wait-result.json
```

也可在一次Python执行中导入使用，脚本的主控与目标限制同样生效：

```python
import sys
sys.path.insert(0, 'scripts')
import codex_chat_bridge as bridge
result = bridge.call('read_thread', {
    'threadId': bridge.WORKERS[0], 'hostId': 'local',
    'turnLimit': 1, 'includeOutputs': False,
    'maxOutputCharsPerItem': 2000,
})
```

## 参数和回传

读取参数：

```json
{"threadId":"目标ID","hostId":"local","turnLimit":1,"includeOutputs":false,"maxOutputCharsPerItem":2000}
```

派发参数：

```json
{"threadId":"目标ID","hostId":"local","prompt":"本轮任务、可改路径、禁改路径、验收口径、停止条件和交接要求"}
```

等待参数：

```json
{"targets":[{"threadId":"目标ID","hostId":"local","afterCursor":"上次对应目标返回的cursor"}],"timeoutMs":30000}
```

第一次等待省略`afterCursor`，以后每个目标保存自己的游标。单次最多等待45秒，以便保持用户沟通。批量等待在第一个目标完成时返回，其余目标未必出现在本次结果中；后续对未收口目标继续有界等待，不把缺少结果当作完成。

返回的`polls`中读取`thread.status`、`latestTurn.status`和`latestAssistantMessage.text`，这些字段可能为空。保存每个目标的`cursor`。派发返回线程ID只证明已接收，必须核对新轮次和最终回复，错误、审批请求或需要用户输入不得冒充通过。

## 推进规则

业务分工、文件归属、依赖并行、共享资源与治理统一按[工程总纲第十一节](../项目工程实施框架.md#十一多对话实施与整合)执行，本文件只维护身份与通信细节。

调用前读取当前任务及目标聊天最近状态，以用户最新输入为准；从当前状态选择任务，不硬编码某次历史协调轮次。仅发送成功不是完成，收到最终回传后仍需A核对实际正文。通信不会恢复暂停的技术测试；领域只在原聊天最终回复交接，不横向派发。

协作记录粒度按[总纲10.1](../项目工程实施框架.md#101-记录各守其职)：重要事件和最终结果集中记录，游标集中更新，普通等待不每次另建文件；已有验收原始证据保留。

通信超时可能已经投递，不自动重发；先读取目标最新消息和状态。若桌面重启后管道改变，重新从当前Codex环境获取。该桥依赖本机桌面原生协议，应用升级可能需要适配，不能宣称后台永久运行或跨机器通用。A结束本轮后不会因桥接脚本存在而自动唤醒；持续推进期间应保留A的协调轮次并有界等待。

## 验收证据
